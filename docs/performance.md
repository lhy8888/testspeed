# 高带宽与高 RTT 测速设计

本版本把 1G、10G、100G 作为需要覆盖的量级，而不是预先写入界面的测量结果。可否测满还取决于客户端、真实网卡、TCP 窗口、TLS、代理和服务器 CPU。当前云实例只有 5 个可用 CPU 核心；本机回环测试不能证明公网或 100G 网卡的线速能力。

## 单端口、固定并发与持续传输

默认同一个 Go 进程只监听网页/控制端口 8080，下载和上传采用同端口的 WebSocket。默认固定使用 8 路并发，用户可手动选择 1–30 路；自动调整并发是可选模式，不是默认行为。标准 HTTP/1.1 Upgrade 的每路 WebSocket 使用独立 TCP，达到 30 路不需要增加其他测速端口。

后端启动时生成一份 25 MiB 随机数据，并共享准备好的 WebSocket binary 消息，持续发送到连接。数据消息之间不等待新的 HTTP 请求。可选 HTTP 模式的 `stream=1` 也使用持续响应，不是在传完 25 MiB 后重新建立请求。两种方式都避免高 RTT 下每个数据块产生完整请求往返，也不需要为每次发送重新生成随机数据或读取磁盘。

浏览器只会在完整 WebSocket 消息到达后交付数据。下载初始消息为 4 KiB，客户端可按实际吞吐将消息调整到 1 KiB–1 MiB 范围内的 2 的幂，兼顾慢速链路及时计量与高速链路的消息调度成本。WebSocket 压缩明确关闭。

25 MiB 是本项目的缓存块大小，不能仅凭这个数字断言它与 FAST 早期实现完全相同。重复数据仍需明确禁用 HTTP 压缩、缓存和中间代理转换；否则重复块可能被压缩而使测速失真。

客户端把测量工作放在 Web Worker 中，只向界面发送低频统计，接收并丢弃下载数据，不保留整个阶段的数据。上传复用不可变随机数据块，服务器逐段读取 WebSocket binary 消息，不要求消息完整结束才计数，单条消息上限为 4 MiB。可选 HTTP 上传通过 Blob 引用组合大请求体，避免为每条流复制数百 MiB 的 JavaScript 数组；后端也不保存完整 HTTP 请求体。

WebSocket 上传复用一份 25 MiB Blob 的 1 MiB 切片，每连接最多排队 4 MiB。共享发送循环每轮为每条有空间的连接提交最多 4 条消息，再通过 MessageChannel 让出一个任务，让网络、取消和统计继续运行；所有连接都没有发送空间时，等待 2 ms 后检查。发送不使用固定周期来限定吞吐。bufferedAmount 仅用于控制排队，不作为测速字节计数。取消时先删除服务端会话，让关联连接立即停止，而不是等待浏览器把排队数据发完。

## 上传为什么由服务器计数

客户端提交一个上传请求不代表字节已经到达服务器，等待整块上传完成确认又会受到 RTT 和未完成尾部影响。新协议在服务端为每个上传阶段创建短期测量会话，在单调时钟窗口内统计**实际收到的字节**。客户端轮询该会话得到速度与进度，因此慢速上传不必先传完大块数据，高速上传也不用依赖每一块的往返确认计算速率。

会话和传输数量有上限，数据不落盘。测试结束或取消后会清理会话；服务进程退出也会清除状态。

## RTT、带宽时延积与预热

延迟越大，维持高速传输所需的在途数据越多：

`带宽时延积（字节）= 速率（bit/s） × RTT（秒）÷ 8`

以 100 ms RTT 为例：

| 带宽 | 在途数据需求 |
| --- | ---: |
| 1 Gbps | 12.5 MB |
| 10 Gbps | 125 MB |
| 100 Gbps | 1.25 GB |

因此「足够大的循环内存块」不是唯一条件：TCP 收发窗口、拥塞窗口及多个流的总在途数据都必须足够。浏览器 JavaScript 无法直接修改 TCP 窗口或拥塞控制算法。页面显示的带宽时延积是根据测得速率和 HTTP RTT 的估算，不是内核 TCP 窗口读数。

客户端根据空闲 RTT 延长预热。默认手动模式固定使用所选并发，便于比较 1、8、30 路等不同设置；可选自动模式会尝试增加连接并观察吞吐增益。传输回退导致容量不足时，页面明确显示原请求值与调整后的值。多条连接共享同一个测量窗口，按总字节量计算速率，不能简单相加各请求在不同时间测出的速度。

## WebSocket TCP 与可选 HTTP 连接池

默认 WebSocket 使用独立的 HTTP/1.1 升级连接，服务端通过实际接收连接的 ID 统计当前及峰值 TCP 数，不能只显示用户填写的数字。经过反向代理时，这个数反映代理到后端的连接，仍不能称为浏览器到公网代理的 TCP 数。

`TEST_TRANSPORT=http` 可选择普通 HTTP 传输。HTTP/1.1 浏览器通常每个 origin 最多使用 6 条连接，HTTP/2 可能将多条 HTTP 请求复用到一条 TCP；单个网页 origin 只分配最多 4 路 HTTP 测速请求，为上传统计和延迟探测保留连接。这些 HTTP 限制不作为默认 WebSocket 模式的 30 路上限。

HTTP 模式可显式配置 `MEASUREMENT_PORTS=8081,8082,8083,8084`，由同一 Go 进程提供四个独立 HTTP/1.1 数据连接池；四个均可达时最多 24 路。每个端口仍是同一台服务器上的同一个节点，不引入其他节点或进程。使用额外端口时须开放、映射相应端口，并保持浏览器收到的地址一致；HTTPS 网页访问的所有测量地址须使用可信 TLS。

反向代理应允许 WebSocket Upgrade。普通 HTTP 模式若被代理合并为同一 HTTP/2 连接池，或排队到单条上游连接，实际并发会下降。无论使用哪种传输，页面都区分逻辑传输数与服务端实际观测到的 TCP 数。

## 测速前探测与传输回退

取得空闲 RTT 后、正式测速前，默认模式先在网页端口打开一条 WebSocket 探测连接，接收 ready 信息和 4 KiB 有限 binary 数据。超时随 RTT 调整为 5–8 秒；探测数据不进入正式测速字节计数。WebSocket 不可用时，会先验证 HTTP 下载路径，再在本次测速开始前回退；默认网页单端口的 HTTP 回退最多 4 路，并明确显示并发调整及代理升级检查提示。

HTTP 探测并行向配置中的各个数据 origin 请求 16 KiB（16384 字节）有限长度下载，使用唯一 nonce 和 `cache: no-store`。读到首个有效非空数据块后取消剩余响应，超时为 1.5–8 秒。部分 origin 不可用时重新计算槽位：两个独立数据 origin 最多 12 路，四个最多 24 路；全部独立数据 origin 不可用时，确认主站下载路径后回退到最多 4 路的网页 origin。主站测量路径也不可用时明确报错。

单端口不等于单线程或单连接。默认 WebSocket 可在同一端口使用 8 路或最多 30 路独立连接，Worker 同时处理多条网络连接，Go 服务并发处理传输。只有普通 HTTP 回退才受上述 4 路容量限制；用户请求 8 路或 30 路而实际使用 4 路时，页面会明确显示调整。

这项回退在正式测量窗口开始前完成，同一次测速的下载和上传使用确定后的来源，不在测速中途切换或混合不同来源的已计量字节。可达性结果不覆盖原配置；下一次测速重新探测，因此端口恢复后可以恢复多连接池容量。取消或离线会停止探测，避免随后自动发起回退测量。

## 部署到 10G / 100G 机器时

- 先用原生工具验证实际路径与服务器容量，再比较浏览器测量；浏览器 CPU、内存拷贝和 TLS 可能先成为瓶颈。
- 采用足够长的测量窗口，尤其是高 RTT 或大窗口 TCP 的慢启动阶段。不要用单个瞬时峰值代表持续带宽。
- 检查网卡、驱动、RSS 多队列、CPU 亲和性及 NUMA，避免流量和 TLS 都集中到一个核心。
- 检查 TCP 自动调优范围。需要的总窗口可用上表估算，多个连接分摊；增大内核缓冲上限必须结合服务器内存预算和并发用户数。
- 禁用测速代理的压缩、缓存、上传及下载缓冲，保留实际流式传输。

当前云实例观测到 `tcp_rmem` 自动调优上限为 32 MiB、`tcp_wmem` 上限为 4 MiB。这个实例没有经过真实 100G 链路验证。程序不会静默修改宿主机的全局 TCP 参数。

例如在有权限的专用高速服务器上，管理员可评估以下上限，结合实际 BDP 与内存预算测试后再应用；它们不是所有机器的默认推荐值：

```text
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728
net.ipv4.tcp_rmem = 4096 131072 134217728
net.ipv4.tcp_wmem = 4096 16384 134217728
```

## 测量后端容量

本项目提供原生 HTTP 测量程序，不受浏览器每 origin 连接池限制：

```sh
go run ./tools/throughput -url http://127.0.0.1:8080 -streams 1,4,12,24 -duration 3s
```

它只测试已获授权的节点，在统一计时窗口内读取真实持续数据，输出字节数、Gbps、连接数和错误数。回环结果反映此机器的 HTTP/内存/CPU 路径能力，不能直接用作网卡线速或浏览器性能承诺。默认的 100G 测试窗口可产生约 125 GB 有效载荷，运行前应考虑实际链路流量。

以下是 2026-10-11 此前 HTTP 多端口版本在 5 核云实例上的历史结果；每组预热 0.5 秒、测量 3 秒，全部零传输错误，不作为当前 WebSocket 实现的性能结果。

| 测速流 / 观测 TCP | 下载有效载荷吞吐 |
| ---: | ---: |
| 1 / 1 | 48.59 Gbps |
| 4 / 4 | 85.93 Gbps |
| 12 / 12 | 96.10 Gbps |
| 24 / 24 | 83.92 Gbps |

这也说明并发越多不一定越快，CPU 调度和内存路径会达到瓶颈。相同实例的真实 Chromium 浏览器 24 流完整测试为下载 9.22 Gbps、上传 7.28 Gbps；浏览器与原生客户端的结果不能混用。完整验证范围见 [validation.md](validation.md)。
